# Technical Deep-Dive Playbooks

<!-- Load this file when the system prompt requests technical deep-dive playbooks. Each playbook is a 10-15 minute focused conversation that validates architecture decisions in one domain. -->

After Phase 3, offer one focused spike: **RAG and Retrieval**, **Agent Design**, **PTU Sizing and Cost**, or **Security and Private Networking**. Pick the one most relevant to the stated use case. Run through 6-8 questions — skip any already answered in earlier phases.

## Playbook 1 — RAG and Retrieval Spike

**Goal:** Validate that the retrieval pipeline is production-ready — correct chunking strategy, well-sized index, measurable quality, and a defined evaluation loop.

| # | Question | Good signal | Weak signal - Probe | SA insight |
|---|----------|-------------|---------------------|------------|
| 1 | Walk me through your end-to-end RAG query flow. What happens between the user submitting a question and the answer appearing? | Describes: embedding the query, hybrid search (BM25 + vector) against AI Search, optional semantic reranking, results injected into system prompt, GPT-4o generates grounded answer. | "We send the question to the model and it searches automatically." Ask: *Where does the retrieval happen — inside the model or in a separate step?* | Agent Service has a built-in file search tool, but for enterprise corpora use an explicit AI Search tool call so you control chunking, index schema, and retrieval parameters. Hybrid search (`query_type=semantic`, `query_language=en-us`) consistently outperforms pure vector on enterprise document sets. |
| 2 | What is your chunking strategy — chunk size, overlap, and how do you handle tables and structured content? | 512–1024 tokens per chunk, 10–15% overlap between adjacent chunks, Azure AI Document Intelligence for PDFs with tables (preserves table structure), separate handling for code blocks. | "We split on paragraph breaks and hope for the best." Ask: *What happens when a key fact spans two paragraphs?* | Azure AI Document Intelligence (Layout model) extracts tables as markdown — chunk the markdown table as a unit, not split across chunks. For legal or financial docs with defined sections, chunk by section heading rather than fixed token count. |
| 3 | What AI Search tier are you planning, and have you sized the index for your document corpus? | S1 tier minimum for production (S2 for high query volume); 1536-dim embeddings for 1M docs require approximately 6 GB vector storage; semantic ranking requires Standard tier; 2 replicas minimum for SLA. S1 starts at USD 245/month per region. | "We will use the free tier." Ask: *Free tier is 50 MB and 3 indexes — at what document volume does your corpus exceed that?* | Estimate: 1M documents at avg 2 KB text = 2 GB text + 1536-dim float32 embeddings ≈ 6 GB vectors. S1 has 25 GB per partition. S2 has 100 GB per partition. Always provision 2+ replicas in production for 99.9% SLA — a single replica has no SLA. |
| 4 | How fresh does the index need to be — are you using an indexer schedule, push API, or event-driven updates? | Indexer schedule (every 5–60 min) for blob/SharePoint sources; push API for real-time updates from application code; soft-delete detection configured to remove deleted documents; understands pull vs push trade-offs. | "We will rebuild the index every night." Ask: *What is your acceptable staleness window, and how large is the corpus? A full rebuild on 10M docs takes hours.* | AI Search indexer supports soft-delete detection via a metadata field (e.g. `isDeleted=true`) — without this, deleted source documents remain in the index permanently. For Blob sources use the change detection policy. For event-driven freshness, the push API (REST POST to `/indexes/{name}/docs/index`) is the lowest-latency option. |
| 5 | How are you evaluating retrieval and generation quality — what metrics, what dataset, and where does it run? | `azure-ai-evaluation` SDK v1.14.0+; groundedness evaluator as primary gate (score ≥ 3.5/5 minimum, 4.0/5 for production); golden dataset of 100+ question-answer-context triples version-controlled; evaluation runs in CI on every prompt or model change. | "We will ask users if it is good." Ask: *How would you detect if a prompt change degraded answer quality for a specific document category before it reached users?* | Groundedness score below 3.5/5 on the golden dataset is a red flag — the model is fabricating answers not grounded in retrieved documents. Run evaluation as a CI gate on every PR that changes the system prompt, chunking strategy, or model version. Store results in Azure ML experiments for trend tracking. |
| 6 | How are you handling multi-turn conversations — does retrieval happen on every turn, and how do you handle pronoun resolution? | Query rewriting before retrieval on every turn: condense conversation history + new user message into a standalone query before embedding and searching; adds approximately 100 ms latency but prevents pronoun resolution failures. | "We send just the latest message to search." Ask: *What happens when a user asks "what about the second option?" with no prior context in the query?* | Pattern: call GPT-4o mini with system prompt "rewrite this conversation into a standalone search query" before each retrieval call. Cost is minimal (GPT-4o mini ≈ USD 0.15/1M input tokens). Without query rewriting, multi-turn RAG degrades significantly on follow-up questions. |
| 7 | How are you handling questions that require structured data — SQL queries, tables, or numeric lookups that vector search cannot answer reliably? | Text2SQL pipeline for tabular data (separate from vector RAG): natural language question routed to a SQL generation agent, query executed against Azure SQL or Synapse, result returned as structured text. Vector RAG for prose documents; Text2SQL for structured data — separate retrieval paths. | "We index all our Excel files into AI Search." Ask: *If a user asks "what was the revenue in Q3 2024 by region", can a vector search over indexed spreadsheet text reliably return the exact number?* | Vector search over table data is unreliable for precise numeric queries. Route structured data questions to a Text2SQL agent tool. Classify query intent first (prose vs structured) using a classifier prompt, then route to the appropriate retrieval path. |
| 8 | What happens when the answer is not in your knowledge base — what does the user see? | Explicit system prompt instruction: "If the answer is not in the provided documents, respond: I do not have that information in my knowledge base. Do not speculate." Tested in evaluation with out-of-scope questions. Fallback escalation path defined. | "The model will figure it out." Ask: *What happens if a user asks about something outside your document corpus — does the model answer from its training data?* | Without an explicit fallback instruction, GPT-4o will answer from its training data and may hallucinate plausible-sounding but incorrect answers. Test fallback explicitly in your golden dataset with 10–20% out-of-scope questions. The model should score 5/5 groundedness on these (correctly refusing to answer). |

## Playbook 2 — Agent Design Spike

**Goal:** Validate that the agent architecture is reliable, observable, and secure — correct `max_turns`, well-described tools, defined memory strategy, and explicit failure handling.

| # | Question | Good signal | Weak signal - Probe | SA insight |
|---|----------|-------------|---------------------|------------|
| 1 | What is your expected agent loop depth — how many tool calls does a typical task require, and how have you set max_turns? | max_turns set to 2x the expected tool call count (e.g. task needs 3 tools so max_turns = 6-8 to allow retries); 30-second timeout per tool call; understands unbounded loops are a cost and reliability risk. | We have not set max_turns. Ask: What happens if a tool call fails and the agent retries indefinitely — what is your cost ceiling per conversation turn? | Default max_turns in Agent Service is 10 — too low for complex multi-tool tasks, too high for simple Q&A. Set explicitly. A runaway agent with no max_turns ceiling can exhaust token quota in minutes. Always instrument cost-per-session in Application Insights. |
| 2 | How have you written your tool descriptions — do they tell the model when to use the tool, when NOT to use it, and what format it returns? | Tool description pattern: Use when X. Do not use for Y. Returns Z format. All three clauses present; parameters have type annotations; return format documented with an example value. | We named the tool and described what it does. Ask: If the agent has both a search tool and a database tool, how does it know which one to call? | Tool selection is pure prompt engineering — the model picks tools based on name and description alone. Poor descriptions cause wrong tool calls, the single biggest source of agent reliability failures. Test each tool description with 20 diverse queries in isolation before integrating. |
| 3 | What is your memory strategy — Basic Agent Setup or Standard Agent Setup, and is that an architecture-time decision? | Knows the difference: Basic = Microsoft-managed Cosmos DB + Blob (no customer VNet, no CMK); Standard = customer-provisioned Cosmos DB + Blob + AI Search in customer subscription (VNet, CMK, full data control). Understands cannot migrate between them after provisioning. | We will decide later. Ask: If your security team requires conversation history never leaves your tenant boundary, which setup do you need — and can you change it after go-live? | This is the most critical Foundry architecture decision customers get wrong. You CANNOT migrate Basic to Standard — Cosmos DB and Blob are provisioned with different configurations. Decide before writing any agent code. Standard Agent Setup adds approximately USD 50-150/month at low volume. |
| 4 | How are you handling tool failures — network timeouts, API errors, and unexpected return formats? | Two-level error handling: (1) retry logic inside the tool function (exponential backoff, 3 retries); (2) structured error dict returned to the agent so it can reason about the failure; agent system prompt instructs how to handle tool errors explicitly. | We let the agent handle it. Ask: What does the agent do if a tool call times out — does it retry, tell the user, or hallucinate a plausible result? | Without structured error returns, the agent frequently hallucinate a plausible-sounding result when a tool fails silently. Return a structured error dict from every tool. Add instruction to system prompt: If a tool returns an error dict, inform the user and do not proceed. |
| 5 | For multi-agent architectures — how are you routing between agents, and how do you prevent routing loops or ambiguous handoffs? | Uses MAF or LangGraph; each agent has mutually exclusive jurisdiction defined in its system prompt; coordinator has explicit routing rules; handoff includes full context; loop detection via max_turns on the coordinator. | We will have agents call each other. Ask: If Agent A and Agent B both believe they can handle a query, which one wins — and what prevents them from passing it back and forth indefinitely? | Mutual exclusivity in agent system prompts is the key. Bad: Agent A handles customer questions. Agent B handles product questions. Good: Agent A handles ONLY billing. Agent B handles ONLY product features. Never hand off to each other — escalate to coordinator. |
| 6 | How are you handling human-in-the-loop scenarios — when does the agent pause for human approval before acting? | requires_action status events monitored in the polling loop; escalation path designed before go-live (webhook to Teams or Slack); timeout behaviour defined; tested with scenarios where approval is withheld. | We have not thought about that yet. Ask: If the agent is about to send an email to 10,000 customers, what prevents it from proceeding without a human review? | Agent Service emits requires_action events when using approval tools. Your polling loop must handle these explicitly — most teams build the happy path only and discover the approval interrupt is broken in production. Design and test the escalation UX before launch. |
| 7 | How are you securing tool access — using agent identity or user identity, and how are you preventing privilege escalation? | On-behalf-of (OBO) flow for user-scoped data access; tool permissions scoped to minimum required (Azure AI User, not Contributor); no broad resource group permissions for agent identity; tool code reviewed for prompt injection risks. | The agent uses a service principal with Contributor on the resource group. Ask: If a malicious user crafts a query to make the agent read another user data, what prevents that? | Agent identity should be Azure AI Inference Deployment Operator or Azure AI User — never Contributor. For tools accessing user-scoped data (email, SharePoint, CRM), implement OBO flow. Without OBO, a single service principal can access all users data across the tenant. |
| 8 | How are you evaluating agent performance end-to-end — task completion rate, tool call accuracy, and response quality? | AgentEvaluator (broader preview Feb 2026) in azure-ai-evaluation; task completion rate as primary metric; tool call accuracy tracked per tool; end-to-end latency per turn in Application Insights; regression suite of 50+ test scenarios run in CI. | We will know if it works when users complain. Ask: How would you detect a 10% regression in task completion rate after a system prompt change, before it reached users? | AgentEvaluator reached broader preview in February 2026. The most actionable metric is tool call accuracy (did the agent call the right tool with the right arguments?) — more diagnostically useful than end-to-end response quality for debugging. |

## Playbook 3 — PTU Sizing and Cost Spike

**Goal:** Validate that the team has a defensible model cost estimate, a PTU vs PAYG decision, a spillover configuration, and a plan for the AzureML SDK v1 EOL deadline.

| # | Question | Good signal | Weak signal - Probe | SA insight |
|---|----------|-------------|---------------------|------------|
| 1 | How have you sized your PTU commitment — what is your peak TPM requirement and how did you calculate it? | Peak RPM x avg tokens per request = peak TPM; for GPT-4o approximately 2,500 TPM per PTU; commitment sized at peak TPM / 2,500 with 20% headroom; validated with a load test before purchase; separate sizing for input vs output token ratios. | We guessed 10 PTUs. Ask: What is your expected peak concurrent users and average prompt + completion token count per request — have you measured it? | Rule of thumb for GPT-4o (Q1 2026): 1 PTU ≈ 2,500 TPM sustained. GPT-4o mini: ≈ 5,000 TPM per PTU. PTU commitments are 1-month or 1-year terms — oversizing wastes budget, undersizing causes 429 throttling at peak. Always load test before committing. |
| 2 | What is your spillover configuration — what happens when PTU capacity is saturated and you receive 429 responses? | APIM policy configured: on 429 from PTU deployment, retry to GlobalStandard secondary; APIM logs PTU utilisation metric; alert fires when spillover exceeds 10% of total requests; team understands GlobalStandard is billed per token. | We have not configured spillover. Ask: If 500 users hit the system simultaneously and PTU is at capacity, what do users experience — a timeout, an error, or transparent failover? | APIM is the canonical spillover mechanism for Foundry. Design your system to operate at 100% GlobalStandard (PTU is a cost optimisation, not a hard dependency). Target: PTU handles the 80th percentile load; GlobalStandard absorbs peak spikes transparently. |
| 3 | At what utilisation does PTU break even vs pay-as-you-go — have you modelled both scenarios at your expected traffic profile? | Break-even at approximately 70-75% average PTU utilisation; has modelled PAYG and PTU at P50 and P95 traffic; 1-year PTU commitment offers 40-60% savings over PAYG at full utilisation; knows that at 40% average utilisation PAYG is cheaper. | PTU is always cheaper. Ask: What is your expected average utilisation across a 24-hour period including overnight off-peak — is it above 70%? | At 50% average utilisation, PAYG is almost always cheaper than PTU. The break-even crossover (≈70-75%) is the most important number in the PTU decision. Model: monthly PTU cost vs (expected monthly tokens x PAYG token rate). Many customers buy PTU before measuring their actual load profile. |
| 4 | How are you sizing AI Search — what tier, replica count, and how have you estimated storage requirements? | S1 tier minimum for production (25 GB per partition, USD 245/month); 2 replicas for 99.9% SLA; S2 (100 GB per partition) for corpora > 20 GB; storage estimated as (doc count x avg chunk size in bytes) + (doc count x embedding dims x 4 bytes for float32). | We will start with S1 with 1 replica and scale later. Ask: A single replica has no SLA — what is the business impact of AI Search downtime on your application? | S1 with 2 replicas is the minimum production configuration (≈ USD 490/month). Semantic ranking requires Standard tier (S1+). Storage estimate for 1M docs at 2 KB avg text + 1536-dim float32 embeddings ≈ 8 GB — fits comfortably in S1 with one partition. Scale partitions before replica count. |
| 5 | What are the platform-level costs beyond the model — Cosmos DB, Blob, Application Insights, APIM, and the Foundry resource itself? | Foundry Resource has no charge (platform is free); Cosmos DB serverless ≈ USD 0.25 per million RUs; Blob Storage ≈ USD 0.018/GB/month; Application Insights ≈ USD 2.88/GB ingested; APIM consumption tier ≈ USD 3.50 per million calls. Has estimated these at expected scale. | We are not thinking about those costs yet. Ask: For 10 tool calls per session at 10,000 sessions per month, have you estimated the Cosmos DB read/write cost for storing conversation history? | Application Insights at verbose logging can exceed model cost at high volume — set sampling rate (1% for > 100 RPS). Cosmos DB is the most common surprise cost for agent workloads: each tool call writes a message record. Model Cosmos DB cost early. |
| 6 | If you are using AzureML SDK v1 anywhere in your pipeline, do you have a migration plan ahead of the June 30 2026 EOL? | Has inventoried all AzureML SDK v1 dependencies in requirements.txt; migration plan to azure-ai-projects v1.x or openai SDK via Foundry compatibility endpoint; knows CLI v1 already reached EOL September 30 2025; migration work is scheduled with buffer before June 30 2026. | We will deal with it later. Ask: June 30 2026 is less than 4 months from now — what happens to your security compliance posture if SDK v1 stops receiving security patches on that date? | AzureML SDK v1 EOL is a hard security deadline, not just a deprecation notice. After June 30 2026, Microsoft will not patch security vulnerabilities in azureml-core, azureml-train, or azureml-sdk. Audit now: search requirements.txt for any azureml- package. |

## Playbook 4 — Security and Private Networking Spike

**Goal:** Validate that authentication, private networking, CMK scope, and RBAC are production-ready — no API keys in code, private endpoints configured correctly, and Standard Agent Setup hardened after provisioning.

| # | Question | Good signal | Weak signal - Probe | SA insight |
|---|----------|-------------|---------------------|------------|
| 1 | How are you authenticating to Foundry and its dependent services — API keys, Managed Identity, or workload identity federation? | DefaultAzureCredential in all application code; Managed Identity assigned at the container or VM level; no API keys in source code, config files, or environment variables; workload identity federation for non-Azure CI/CD; secrets in Key Vault, not .env files. | We are using API keys for now and will switch to Managed Identity later. Ask: How are you rotating those keys today, and where are they stored — can you guarantee they are not in your git history? | API keys in environment variables end up in container image layers, CI/CD logs, and git history. The migration to Managed Identity is the same effort whether you do it now or later. Require DefaultAzureCredential as a go-live gate — it is a one-line code change that eliminates an entire class of credential leak. |
| 2 | Are you using private endpoints for all five PaaS services — Foundry, AI Search, Cosmos DB, Blob, and Key Vault? | All five private endpoints provisioned: privatelink.cognitiveservices.azure.com (Foundry), privatelink.search.windows.net (AI Search), privatelink.documents.azure.com (Cosmos DB), privatelink.blob.core.windows.net (Blob), privatelink.vaultcore.azure.net (Key Vault); public network access disabled on all five; DNS Private Zones configured; agent egress subnet is /24 minimum. | We are planning to add private endpoints before go-live. Ask: If you disable public access on AI Search before the private endpoint DNS record is active, what happens to your indexer pipeline? | The /24 subnet requirement for agent egress is a hard constraint, not a recommendation. Agent Service requires a dedicated subnet of at least 256 addresses. Disable public access ONLY after private endpoints AND DNS Private Zone records are confirmed working. Test with nslookup from inside the VNet. |
| 3 | What is your CMK scope — what does customer-managed key encryption cover and what does it explicitly not cover? | CMK via Azure Key Vault Managed HSM (FIPS 140-2 Level 3); covers: stored model outputs in Foundry resource, index content in AI Search, conversation history in Cosmos DB, documents in Blob. Does NOT cover: data in active GPU memory during inference. Key rotation policy set to 90-day automatic rotation via Key Vault rotation policy. | CMK encrypts everything including inference. Ask: Does customer-managed key encryption apply to data while it is actively being processed through the GPU during a live inference call? | CMK covers data at rest only — this is standard for all cloud ML platforms globally. Data in active GPU memory during inference is not covered. Regulated industries (FinServ, healthcare) must document this scope boundary explicitly for compliance auditors. |
| 4 | How are you handling AI Search indexer egress when Blob Storage has private endpoints and public network access disabled? | Shared Private Link configured from AI Search to Blob Storage (POST to /subscriptions/.../searchServices/{name}/sharedPrivateLinkResources with groupId=blob); AI Search Standard tier required; provisioning takes 5-10 minutes; knows indexer runs in Microsoft-managed infrastructure outside customer VNet. | We have not figured that out yet. Ask: If Blob Storage has no public access and AI Search indexer runs in Microsoft-managed infrastructure outside your VNet, how does the indexer reach the documents? | This is the single most commonly missed networking detail in enterprise Foundry deployments. AI Search indexers run in Microsoft-managed infrastructure — they cannot reach private Blob directly. Shared Private Link is the only supported solution. Requires AI Search Standard tier minimum. |
| 5 | What RBAC roles have you assigned for your application identity and data plane access — have you followed least privilege? | Application Managed Identity: Azure AI User or Azure AI Inference Deployment Operator for model access; Search Index Data Reader for AI Search; no Contributor or Owner on resource group for any application identity; subscription has fewer than 5 Owner role assignments. | The app identity has Contributor on the resource group for simplicity. Ask: What is the blast radius if that service principal credential is compromised — what can an attacker read, modify, or delete? | Contributor on a resource group grants read access to all secrets, ability to deploy new resources, and ability to delete existing data. Application identities must never have Contributor. Use Azure AI User for inference. Run az role assignment list and audit any non-human Contributor or Owner assignments. |
| 6 | For Standard Agent Setup — after Foundry provisions Cosmos DB, Blob, and AI Search into your subscription, what hardening steps do you apply on Day 1? | Disables public network access on Cosmos DB (enabled by default after Standard Setup provisioning): az cosmosdb update --disable-public-network-access; disables Blob public access: az storage account update --default-action Deny; enables CMK on both; configures diagnostic logs to Log Analytics; runs Defender for Cloud assessment before go-live. | We provisioned Standard Setup and it works — we will harden it before go-live. Ask: Have you checked whether Cosmos DB and Blob Storage were provisioned with public network access enabled by default? | When Foundry provisions Cosmos DB and Blob into your subscription via Standard Agent Setup, both resources are created with public network access ENABLED. This is the default Azure resource behaviour. You must explicitly disable it. Treat this as a Day 1 hardening checklist item, not an optional post-launch task. |
